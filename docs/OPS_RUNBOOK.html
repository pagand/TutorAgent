0. Prerequisites - read this first

Everything below depends on the facts on this page. It exists so no procedure later in this document has to re-explain how to authenticate or reach the box. If a later section says "see §0," this is where it points.

Authenticate: AWS SSO

This account uses AWS SSO, not long-lived access keys. Once per shell session (the token lasts several hours, then needs a fresh login):

aws sso login --profile AdministratorAccess-434195712367

This opens a browser to complete the login. If any command below fails with an expired-token or refresh-failed error, this is the fix - run it again.

The profile flag is not optional, and a missing one looks like a different error entirely. There is no default AWS profile configured on a fresh machine. A bare aws command with no --profile and no AWS_PROFILE exported fails with Unable to locate credentials / NoCredentialProviders. That error means "you forgot the profile flag," not "your SSO session expired" - re-running aws sso login will not fix it. Every aws command in this document needs --profile AdministratorAccess-434195712367, or export it once for the whole shell so every later command can drop the flag: 
export AWS_PROFILE=AdministratorAccess-434195712367
This document writes --profile explicitly on most examples anyway, so any single command can be copy-pasted on its own without depending on shell state from an earlier step.

Region is us-west-2 for every resource in this stack (except the ACM certificate for CloudFront, which must live in us-east-1 - that is called out where it matters, in §1). Pass --region us-west-2, or export it once:

export AWS_REGION=us-west-2

Shell access on the box: SSM only, there is no SSH

Port 22 has no ingress rule at all on the instance's security group (terraform/network.tf) - not "locked down," genuinely absent. ssh to the box will hang and time out, not refuse the connection. The only way onto the box is AWS Systems Manager Session Manager, which needs no open port at all - it works over an outbound HTTPS connection the SSM agent on the box initiates itself.

Interactive shell:

aws ssm start-session --target <instance-id> --region us-west-2 --profile AdministratorAccess-434195712367
You land as ssm-user, not ec2-user. The repo is not under this user's home directory. An interactive session drops you into /home/ssm-user (AWS's default for Session Manager), which has nothing in it. To reach the app: 
sudo -iu ec2-user
cd /home/ec2-user/AITutorApp
Every command in this document that runs "on the box" assumes you have done this, or is written as a full path from the start. If a command below only says cd AITutorApp, treat that as shorthand for the two lines above, not something to type verbatim in an ssm-user shell.
SSO login and --profile are a laptop concept only - not needed once you're on the box. Every aws command targeting the box from your laptop (start-session, send-command, describe-instances, etc.) needs the SSO login and profile above. But any aws command run on the box itself (inside an SSM session, or inside scripts/snapshot.sh/ec2-bootstrap.sh) authenticates automatically via the instance's IAM role - no login, no profile, no credentials file. If you see aws s3 cp or aws sts get-caller-identity with no --profile anywhere in a script in this repo, that is why - it is expected to run on the box, not your laptop.

Non-interactive (most automation and every aws ssm send-command example in this document uses this shape - these run as root, so they use full paths and don't need the sudo -iu ec2-user step above):

CMD_ID="$(aws ssm send-command --region us-west-2 --profile AdministratorAccess-434195712367 \
  --instance-ids <instance-id> \
  --document-name AWS-RunShellScript \
  --parameters commands='["cd /home/ec2-user/AITutorApp && docker compose ps"]' \
  --query 'Command.CommandId' --output text)"

aws ssm get-command-invocation --region us-west-2 --profile AdministratorAccess-434195712367 \
  --command-id "$CMD_ID" --instance-id <instance-id> \
  --query '{Status:Status,Output:StandardOutputContent,Error:StandardErrorContent}' --output json

The first call returns immediately with a command id; the command itself runs asynchronously on the box, so the second call is what actually shows the result - if you query it too soon it reports InProgress rather than a finished status, just re-run the same get-command-invocation call again a few seconds later.

1. System map

Single-distribution architecture, Stage 5. One CloudFront distribution serves both the frontend (static export from S3) and the API (/api/*, proxied to one EC2 instance behind a static Elastic IP). api.air.da-tu.ca no longer exists — there is one domain, air.da-tu.ca, and one registrar CNAME pointing it at CloudFront. TLS terminates at CloudFront; the box only ever speaks plain HTTP.

The CloudFront-to-origin hop is not encrypted, by design. Origin traffic is not encrypted between CloudFront and EC2. This is accepted because the threat model prioritizes operational reliability over protection from network interception. CloudFront requires a publicly-trusted certificate to speak HTTPS to a custom origin, and keeping one alive would mean keeping certbot — whose renewal path never actually worked (it checked a host path certbot never wrote to; deleted rather than fixed). Mitigated two ways: the origin's security group admits port 80 only from CloudFront's published origin-facing IP ranges (nothing else can reach the box at all), and nginx rejects any request missing a shared secret CloudFront attaches on every request (X-Origin-Secret). Interception itself would need a position on the path between a CloudFront edge and the Elastic IP — backbone/ISP-level access, not something reachable from a student's own network.
ServiceWhat it isReachable fromState
dbpostgres:16-alpinecompose network only, port 5432 never exposed to hostpostgres_data named volume
apiFastAPI backend, built from the repo Dockerfilecompose network only (port 8000, expose not ports) — nginx is the only path inchroma_data volume (RAG store); prod/data read-only bind mount

What's not in Docker: the Elastic IP, security group, IAM roles, CloudWatch alarms, Cost Anomaly Detection, Budgets, and the CloudFront distribution (frontend origin + the /api/* behavior pointed at the EIP) all live in Terraform (terraform/), applied from a laptop with SSO credentials — never from the box itself. The two monthly EventBridge Scheduler rules that used to boot the box for certificate renewal are gone along with certbot; nothing boots the box automatically anymore.

Why the Elastic IP still exists even though api.air.da-tu.ca doesn't: CloudFront's /api/* origin (terraform/frontend.tf) points at aws_eip.api.public_dns, which has to stay stable across every stop/start — a plain EC2 public IP changes on every start, and this box is deliberately stopped between exams. Without the EIP, CloudFront's origin config would go stale on the very first post-exam stop/start. The EIP has prevent_destroy in Terraform for this reason.

The Elastic IP costs money whether the instance is running or not - do not "optimize" it away. The line item that shows up in Cost Explorer as "Amazon Virtual Private Cloud" is not VPC infrastructure at all - it is purely the public IPv4 charge on this EIP, usage types USW2-PublicIPv4:IdleAddress and USW2-PublicIPv4:InUseAddress, $0.005/hr, roughly $3.60/mo, billed continuously including while the instance is stopped. That is the correct tradeoff: it is what keeps the CloudFront origin hostname stable across stop/start (see above). The older rationale for the EIP, a Route 53 A record and a certbot TLS cert, is obsolete - both were deleted in Stage 5. Releasing the EIP to save ~$3.60/mo would break the CloudFront origin the next time the box stops and starts.
DNS / custom domain: live, confirmed 2026-08-05. The ACM certificate for air.da-tu.ca is ISSUED in us-east-1, and the CloudFront distribution (EAU1TO5IJG1RT) now has air.da-tu.ca attached as an alias. Both registrar CNAMEs (the ACM validation record, and air.da-tu.ca → d2u3k75qofedmd.cloudfront.net) have propagated - dig air.da-tu.ca resolves through to CloudFront, and curl -sI https://air.da-tu.ca/ returns a real 200. This was previously pending for most of Stage 5; the fallback CloudFront domain (https://d2u3k75qofedmd.cloudfront.net) still works identically and is left in this document's examples below since it needs no DNS at all, but https://air.da-tu.ca is now the real, working public URL.

2. Starting and stopping

aws ec2 start-instances --region us-west-2 --profile AdministratorAccess-434195712367 --instance-ids $INSTANCE_ID
aws ec2 stop-instances  --region us-west-2 --profile AdministratorAccess-434195712367 --instance-ids $INSTANCE_ID

Get $INSTANCE_ID from §0's lookup - the id changes any time the box is replaced (e.g. a Terraform user_data change), so don't hardcode it in scripts or muscle memory.

On every boot, aitutor-bootstrap.service (a systemd oneshot installed by user_data.sh.tftpl at first boot) runs scripts/ec2-bootstrap.sh automatically: pulls origin/main, renders .env from SSM Parameter Store, refreshes CloudFront's origin-facing IP list, builds and starts all four containers, waits for api to report healthy, and re-seeds participants. No backup cron is installed anymore (§5b), and no certbot step anymore — TLS terminates at CloudFront, so the box only ever renders one nginx config. Observed timing this stage: SSM agent online almost immediately; full bootstrap (cold, no build cache) around 3 minutes; a warm re-run (cache hit) under a minute.

Self-modifying script gotcha: a code change to ec2-bootstrap.sh needs two triggers to actually take effect on an already-running box. The script's own first real action is git reset --hard origin/main, which rewrites the very file the running process is executing. The already-running process keeps reading its own stale in-memory/buffered copy to completion — so the first trigger after a push correctly updates the repo on disk, but still runs the old logic end to end (observed live during Stage 5: a first re-trigger after deleting plain.conf/tls.conf still tried to cp the now-deleted file, and separately, a first re-trigger after adding LLM_PROVIDER=google to the .env heredoc still rendered .env without it). A second systemctl reset-failed aitutor-bootstrap.service && systemctl start aitutor-bootstrap.service reads the file fresh and runs correctly. A full aws ec2 reboot-instances does not have this problem — systemd starts a genuinely new process reading the current file from the start. When in doubt after changing this script, trigger it twice, or reboot instead of using the SSM one-liner.

Watch it live (§0 for the instance id lookup and authentication):

aws ssm start-session --target $INSTANCE_ID --region us-west-2 --profile AdministratorAccess-434195712367
sudo journalctl -u aitutor-bootstrap.service -f

3. Health checks

HTTP 200 from curl is not evidence the site works. This is not a hypothetical - it happened. The deployed frontend once served a blank white page to every single visitor while every curl-based check in this document reported success. Cause: terraform/frontend.tf's CloudFront response-headers policy set script-src 'self' with no 'unsafe-inline'. Next.js's static export bootstraps through inline <script>self.__next_f.push(...)</script> tags carrying the RSC flight payload - CSP blocked all of them, React threw Error: Connection closed., and the server-rendered markup was wiped. curl -sI against the page still returned a clean 200 the entire time, because curl neither executes JavaScript nor enforces CSP - it only ever saw the initial HTML, not what the browser did with it after. Fixed to script-src 'self' 'unsafe-inline' (see the comment above aws_cloudfront_response_headers_policy.frontend in terraform/frontend.tf), applied, CloudFront invalidated. Every curl-based check below only verifies that a server responded - none of them can catch a client-side rendering failure like this one. Load the deployed page in a real browser and confirm visible text is present before trusting any curl result as "the site works."

One-command "is it up", no interactive session needed (see §0 for $INSTANCE_ID and this exact send-command / get-command-invocation shape):

CMD_ID="$(aws ssm send-command --region us-west-2 --profile AdministratorAccess-434195712367 --instance-ids $INSTANCE_ID \
  --document-name AWS-RunShellScript \
  --parameters commands='["cd /home/ec2-user/AITutorApp && docker compose ps"]' \
  --query 'Command.CommandId' --output text)"
aws ssm get-command-invocation --region us-west-2 --profile AdministratorAccess-434195712367 \
  --command-id "$CMD_ID" --instance-id $INSTANCE_ID \
  --query '{Status:Status,Output:StandardOutputContent,Error:StandardErrorContent}' --output json

Or interactively (see §0 for the instance id lookup and the sudo -iu ec2-user step): aws ssm start-session --target $INSTANCE_ID --region us-west-2 --profile AdministratorAccess-434195712367, then sudo -iu ec2-user, cd /home/ec2-user/AITutorApp && docker compose ps. Healthy looks like all four containers Up, with api, db, and streamlit additionally showing (healthy), nginx genuinely has no healthcheck defined (a plain reverse proxy with nothing to probe), so "running" is the only signal for it. Streamlit and api both build from the same root Dockerfile, which bakes in a healthcheck against port 8000 - correct for api, wrong for streamlit (which serves on 8501), so docker-compose.yml overrides it for the streamlit service with its own probe against http://localhost:8501/_stcore/health. Before this override existed, streamlit inherited the 8000 probe, which always failed, and the container sat permanently unhealthy while working fine - if you ever see that again, it means the override in docker-compose.yml was lost.

4. Promoting code from GitHub to prod

Suggestions only — nothing below is implemented.

The image is built on the box, not locally or in AWS CI. There is no ECR, no CodeBuild, no separate build step anywhere. docker compose up -d --build on the EC2 instance itself is the entire build pipeline.

Today's actual promotion path

  1. Merge to main, push.
  2. Trigger the box to pick it up, there is no automatic boot anymore (§2), so this step is never optional. Run from your laptop, authenticated per §0, with $INSTANCE_ID from §0's lookup: 
    aws ssm send-command --region us-west-2 --profile AdministratorAccess-434195712367 --instance-ids $INSTANCE_ID \
  --document-name AWS-RunShellScript \
  --parameters commands='["sudo systemctl reset-failed aitutor-bootstrap.service", "sudo systemctl start aitutor-bootstrap.service"]'
# if this is the box's first pull of a change to ec2-bootstrap.sh
# itself, run the same command a second time - see the self-modifying-
# script callout in §2.

That's the whole thing. Observed cost this stage: roughly 1–3 minutes depending on build-cache warmth, with automatic rollback-free re-seeding folded in for free. This is genuinely simple, which is the strongest argument for leaving it alone.

5. Changing prod data

Safe mid-exam Adding or editing a participant. prod/seed_participants.py only ever touches token/name/identifier/group/intervention — it never writes status, active_session_id, started_at, or last_seen_at on a row that already exists, so a live student's session is untouched by a re-seed.
Not safe mid-exam Changing server_ready_questions.csv under a student who is mid-attempt. Questions load into memory once at api boot (app/main.py); nothing reloads them live, deliberately — silently swapping questions under an in-progress student would be worse than requiring an explicit restart.

5b. Backups — on demand only, there is no cron

There is no scheduled backup. Do not go looking for one. A nightly 0 2 * * * cron used to be installed by ec2-bootstrap.sh; it was deleted, because it only ran while the instance ran and this box is stopped between exams by design. A single-day, 25-minute exam very likely never crosses 02:00 while the box happens to be up, so the cron was coverage on paper and nothing in practice. Never describe a scheduled backup as coverage in an incident, there isn't one.

The real protection is a dump taken immediately before stopping the box. While the box is stopped, data physically cannot change, so a pre-stop dump is current for the entire stopped period by definition. This is §10 step 7 — do it every time, not just after an exam.

There is deliberately no mid-exam backup step either. docker compose restart loses nothing, and the postgres_data named volume survives a stop/start of the instance. The only events that actually destroy data are instance termination and EBS loss, neither of which a mid-exam pg_dump would have prevented in the window it covers. The recorded failure contingency ("restart services, retain data, resume the exam") is satisfied by the restart alone.

Fixed during Stage 5 (previously a real gap, F2 in the migration plan), and still relevant to the manual runs: BACKUP_S3_URI points at aitutor-backups-<account-id> (a dedicated Terraform-managed bucket, terraform/backups.tf), not the ops bucket. The instance role previously had no PutObject permission on the ops bucket at all, so every `aws s3 cp` silently failed with AccessDenied — backup.sh exited non-zero under set -e. Before this fix, the system would have looked like it had off-box backups and had none. The instance role's IAM policy also now grants GetObject/ListBucket on the backups bucket (previously write-only, so nothing on the box could even read a backup back — no restore path existed at all).

Verify a dump actually landed (from your laptop, authenticated per §0):

aws s3 ls s3://aitutor-backups-434195712367/backups/ --region us-west-2 --profile AdministratorAccess-434195712367
Verified live, 2026-08-05: the backups/ prefix is still empty. No off-box Postgres-only dump exists right now. s3://aitutor-backups-434195712367/backups/ contains zero objects (the snapshots/ prefix, §5c, now has one - a different mechanism, not this one). The backup.sh upload path is correctly wired end to end (IAM fix above, correct bucket, correct permissions) - nobody has run it against production yet. 5c. Instance snapshot and restore

Built 2026-08-05, per the plan in PRELAUNCH_CHECKLIST.md, "Instance snapshot: requirements and plan". Two scripts, two directions:

  • scripts/snapshot.sh - capture. Bundles Postgres (via backup.sh), the chroma_data Docker volume (the Chroma vector store plus llm_cache.db, which lives inside it), a CSV export of all 9 application tables, a point-in-time copy of prod/data, and all four services' container logs into ONE timestamped archive, uploaded to the backups bucket.
  • scripts/snapshot_restore.sh - restore. Takes a bundle and brings a fresh box's Postgres and chroma_data volume up to the captured state.
Not a cron, and not the same thing as §5b's backups. backup.sh is the routine pre-stop Postgres-only dump. snapshot.sh is the heavier, occasional full-instance bundle - run it post-exam and whenever you want a complete offline copy of everything, not every time you stop the box. Both land in the same bucket but under different prefixes (backups/ vs snapshots/), and neither expires: terraform/backups.tf's lifecycle rule was changed 2026-08-04 so current objects in this bucket have no expiry at all, only noncurrent (superseded) versions are pruned.

Capture: bringing the box down to a single restorable bundle

Run this any time you want a full offline copy - a required step post-exam, and worth doing before any risky change (Terraform apply that touches the instance, a manual package upgrade, etc.). Requires the containers to be up, same as backup.sh - run it before stop-instances, not against a stopped box.

# on the box, in /home/ec2-user/AITutorApp, containers running
POSTGRES_USER=aitutor POSTGRES_DB=aitutor_db ./scripts/snapshot.sh
This causes a brief, deliberate api outage. llm_cache.db is a live SQLite file inside the chroma_data volume; tarring it while api is running risks a torn copy. snapshot.sh runs docker compose stop api for the few seconds the volume tar takes, then docker compose start api immediately after. db, nginx, and streamlit are never stopped. Do not run this mid-exam - it is a post-exam / maintenance-window step, same reasoning as §5b's "not a cron."

s3://aitutor-backups-<account-id>/snapshots/aitutor_snapshot_<YYYYMMDDTHHMMSSZ>.tar.gz

Verify it landed (same pattern as §5b):

Restore: bringing a fresh box back to the captured state

Assumes the old instance is gone and Terraform has already created a replacement, or you are restoring onto a fresh box for any other reason. Sequence:

  1. terraform apply creates the instance; ec2-bootstrap.sh runs on first boot and brings the containers up with an empty database (see §2/§3 for confirming bootstrap finished).
  2. Connect over SSM as above, cd into the repo, then download and restore in one step: 
    POSTGRES_USER=aitutor POSTGRES_DB=aitutor_db \
  ./scripts/snapshot_restore.sh \
  s3://aitutor-backups-434195712367/snapshots/aitutor_snapshot_<ts>.tar.gz
    This downloads the bundle, restores Postgres by calling the existing scripts/restore.sh unchanged (pg_restore --clean --if-exists, so it replaces the freshly-seeded participants rows with the captured ones), then restores the chroma_data volume - stopping api for the duration, same brief-outage tradeoff as capture.
  3. Verify: snapshot_restore.sh extracts the bundle into a temp directory it deletes on exit, so check row counts directly against Postgres instead of the (by-then-gone) extracted CSVs: 
    docker compose exec -T db psql -U aitutor -d aitutor_db -c \
  "SELECT 'users', COUNT(*) FROM users UNION ALL SELECT 'participants', COUNT(*) FROM participants;"
    If you want a full per-table comparison against the bundle's own CSVs, download and unpack the same bundle a second time yourself (aws s3 cp ... && tar xzf ...) rather than relying on anything snapshot_restore.sh left behind.
Alembic ordering hazard. Step 1 already ran alembic upgrade head against the fresh box's current main. Step 2 then restores an alembic_version row from the snapshot's dump. If the repo has gained migrations since the snapshot was taken, the restored alembic_version will point at an older revision than the schema actually is, and the next alembic upgrade head will try to re-run migrations that already applied. There is no automatic handling of this today - if the snapshot predates the box's current migration history, check alembic_version after restoring and reconcile it by hand before trusting the schema.
prod/data is NOT restored by this script, on purpose. On a rebuilt box, prod/data (questions + participant manifest) arrives via ec2-bootstrap.sh's own S3 sync from the ops bucket - that is the one authoritative path for getting it onto a box (see §5, update-prod-data.sh). The bundle's prod_data/ copy is a point-in-time record for audit only.

What a restore cannot bring back, regardless: anything that happened after the snapshot (there is no point-in-time recovery or WAL archiving - a snapshot is a single moment, full stop), the instance's surroundings (Elastic IP, CloudFront distribution, SSM parameters, the GitHub deploy key - all come from Terraform and SSM, not this bundle), and the deployed frontend (a separate S3/CloudFront static export, not instance data). Restore is always "Terraform first, then this bundle," never this bundle alone.

What has actually been verified, and what has not (as of 2026-08-05)

Tested locally against seeded, disposable scratch Postgres databases (never against the dev or production database): the Postgres capture-then-restore round trip via backup.sh/restore.sh's non-Docker code path (all 9 tables matched row-for-row after restore), and the CSV export (all 9 tables produced real rows, JSON columns rendered as single JSON-text columns as documented above). Both scripts pass bash -n and were dry-run for their failure paths (missing bundle argument, missing POSTGRES_USER/POSTGRES_DB, nonexistent bundle path all fail immediately with no default target, matching restore.sh's own safety property).

Update, 2026-08-05: the capture side is now proven against real infrastructure, not just reviewed. scripts/snapshot.sh was exercised end to end on the rebuilt box, including the chroma_data Docker-volume capture and the real S3 upload - a bundle from a freshly bootstrapped box came out to about 445 KB. That box also confirmed a cold bootstrap takes about 3 minutes, the app loads 25 questions across 5 skills, and RAG ingestion turns the 7-page source PDF into 21 chunks.

Still NOT tested: scripts/snapshot_restore.sh's restore direction. Postgres restore via restore.sh is proven locally (above), but restoring the chroma_data volume onto a second box, and the full download-then-restore path end to end, have not been exercised for real. Treat restore as reviewed but unproven until it has actually brought a box back from a snapshot once.

10. Exam day runbook

Sequenced from PRELAUNCH_CHECKLIST.md §K, folded into one list:

  1. Snapshot before starting. Take an EBS snapshot of the current (stopped) volume before aws ec2 start-instances, so there's a clean pre-exam restore point. From your laptop, authenticated per §0, with $INSTANCE_ID from §0's lookup (this is the same command used in step 7 below - the box has one root volume, no others): 
    VOLUME_ID="$(aws ec2 describe-instances --profile AdministratorAccess-434195712367 --region us-west-2 \
  --instance-ids $INSTANCE_ID \
  --query 'Reservations[0].Instances[0].BlockDeviceMappings[0].Ebs.VolumeId' --output text)"

SNAP_ID="$(aws ec2 create-snapshot --profile AdministratorAccess-434195712367 --region us-west-2 \
  --volume-id "$VOLUME_ID" --description "aitutor $(date -u +%Y%m%dT%H%M%SZ)" \
  --query 'SnapshotId' --output text)"

# poll until it's done - completed is safe to walk away from,
# pending is not (the underlying volume can still change under it)
aws ec2 describe-snapshots --profile AdministratorAccess-434195712367 --region us-west-2 \
  --snapshot-ids "$SNAP_ID" --query 'Snapshots[0].[State,Progress]' --output text
  2. Start the instance, watch aitutor-bootstrap.service complete over SSM (§2, §3).
  3. Confirm EXAM_DURATION_MS on the box reads 1500000 (25 minutes), not a leftover 20-minute default, and LLM_PROVIDER reads google (see §8's incident row — the code default is the wrong provider): docker compose exec api env | grep -E "EXAM_DURATION_MS|LLM_PROVIDER".
  4. Smoke test one real token end to end (login, answer, hint, chat, submit, results) before handing tokens to students. Confirm the quiz loads 25 questions across 5 skills (confirmed live, 2026-08-05) - a wrong count means the wrong server_ready_questions.csv landed. Check the actual hint/chat content, not just the HTTP status: a 200 with hint_style: "error" means the LLM call silently failed.
  5. Expect a slow first hint. RAG cold start is ~2s measured, but the first real request after boot still pays container warm-up cost on top. Not a bug if the very first hint feels sluggish.
  6. Keep an SSM session open to the box and a port-forward tunnel to Streamlit (§9) for the full exam window, so timer/lock issues can be handled in real time.
  7. Immediately before stopping the instance: take an EBS snapshot (same create-snapshot command as step 1) and run backup.sh on the box (per §0: sudo -iu ec2-user, cd /home/ec2-user/AITutorApp), with BACKUP_S3_URI passed explicitly: 
    DOCKER_DB_SERVICE=db POSTGRES_USER=aitutor POSTGRES_DB=aitutor_db \
  BACKUP_S3_URI=s3://aitutor-backups-434195712367/backups \
  ./scripts/backup.sh
    BACKUP_S3_URI must be passed on the command line - it is not already in an interactive shell's environment. ec2-bootstrap.sh renders BACKUP_S3_URI into the app's .env file, but that file is only read by docker compose's env_file: mechanism for the api/streamlit containers - it is never sourced into an interactive host shell. backup.sh itself runs on the host (it shells out to docker compose exec for the dump, it isn't a container process), and reads BACKUP_S3_URI straight from its own process environment via ${BACKUP_S3_URI:-} (scripts/backup.sh). Omit it and the script does not error - it just silently skips the upload and leaves the dump local-only under ./backups/, which defeats the entire point of a pre-stop backup. Always pass it explicitly, as above, rather than assuming it's already set.
    Verify the upload landed before proceeding (same check as §5b): 
    aws s3 ls s3://aitutor-backups-434195712367/backups/ --region us-west-2 --profile AdministratorAccess-434195712367
    This is the only backup, nothing is scheduled (§5b), and while the box is stopped the data cannot change, so a dump taken right before stopping stays current for the entire stopped period.
  8. Stop the instance once data is safely off-box. It should not sit running between exams.
