1. System map

Single-distribution architecture, Stage 5. One CloudFront distribution serves both the frontend (static export from S3) and the API (/api/*, proxied to one EC2 instance behind a static Elastic IP). api.air.da-tu.ca no longer exists — there is one domain, air.da-tu.ca, and one registrar CNAME pointing it at CloudFront. TLS terminates at CloudFront; the box only ever speaks plain HTTP.

The CloudFront-to-origin hop is not encrypted, by design. Origin traffic is not encrypted between CloudFront and EC2. This is accepted because the threat model prioritizes operational reliability over protection from network interception. CloudFront requires a publicly-trusted certificate to speak HTTPS to a custom origin, and keeping one alive would mean keeping certbot — whose renewal path never actually worked (it checked a host path certbot never wrote to; deleted rather than fixed). Mitigated two ways: the origin's security group admits port 80 only from CloudFront's published origin-facing IP ranges (nothing else can reach the box at all), and nginx rejects any request missing a shared secret CloudFront attaches on every request (X-Origin-Secret). Interception itself would need a position on the path between a CloudFront edge and the Elastic IP — backbone/ISP-level access, not something reachable from a student's own network.

Volume lifecycle docker compose down keeps postgres_data and chroma_data — safe for a routine restart. docker compose down -v destroys both. Never run -v against the live box without a fresh pg_dump in hand first.

What's not in Docker: the Elastic IP, security group, IAM roles, CloudWatch alarms, Cost Anomaly Detection, Budgets, and the CloudFront distribution (frontend origin + the /api/* behavior pointed at the EIP) all live in Terraform (terraform/), applied from a laptop with SSO credentials — never from the box itself. The two monthly EventBridge Scheduler rules that used to boot the box for certificate renewal are gone along with certbot; nothing boots the box automatically anymore.

Why the Elastic IP still exists even though api.air.da-tu.ca doesn't: CloudFront's /api/* origin (terraform/frontend.tf) points at aws_eip.api.public_dns, which has to stay stable across every stop/start — a plain EC2 public IP changes on every start, and this box is deliberately stopped between exams. Without the EIP, CloudFront's origin config would go stale on the very first post-exam stop/start. The EIP has prevent_destroy in Terraform for this reason.

The Elastic IP costs money whether the instance is running or not - do not "optimize" it away. The line item that shows up in Cost Explorer as "Amazon Virtual Private Cloud" is not VPC infrastructure at all - it is purely the public IPv4 charge on this EIP, usage types USW2-PublicIPv4:IdleAddress and USW2-PublicIPv4:InUseAddress, $0.005/hr, roughly $3.60/mo, billed continuously including while the instance is stopped. That is the correct tradeoff: it is what keeps the CloudFront origin hostname stable across stop/start (see above). The older rationale for the EIP, a Route 53 A record and a certbot TLS cert, is obsolete - both were deleted in Stage 5. Releasing the EIP to save ~$3.60/mo would break the CloudFront origin the next time the box stops and starts.
DNS / custom domain: currently pending. The ACM certificate for air.da-tu.ca is PENDING_VALIDATION in us-east-1, and the CloudFront distribution (EAU1TO5IJG1RT) has zero aliases attached - it still serves on the default CloudFront certificate only. Two CNAMEs are outstanding at the registrar: the ACM validation record, and air.da-tu.ca → d2u3k75qofedmd.cloudfront.net. Until both land, air.da-tu.ca does not resolve to this stack at all. This blocks only the custom domain and its cert - everything else is fully usable today over https://d2u3k75qofedmd.cloudfront.net, which already has working HTTPS via the default CloudFront cert.

2. Starting and stopping

aws ec2 start-instances --region us-west-2 --instance-ids <id>
aws ec2 stop-instances  --region us-west-2 --instance-ids <id>

Find the current instance ID with terraform output instance_id (from terraform/) or by tag: aws ec2 describe-instances --filters Name=tag:Name,Values=aitutor-app Name=instance-state-name,Values=running,stopped. The ID changes any time the box is replaced (e.g. a Terraform user_data change) — don't hardcode it in scripts or muscle memory.

On every boot, aitutor-bootstrap.service (a systemd oneshot installed by user_data.sh.tftpl at first boot) runs scripts/ec2-bootstrap.sh automatically: pulls origin/main, renders .env from SSM Parameter Store, refreshes CloudFront's origin-facing IP list, builds and starts all four containers, waits for api to report healthy, re-seeds participants, and installs the nightly backup cron. No certbot step anymore — TLS terminates at CloudFront, so the box only ever renders one nginx config. Observed timing this stage: SSM agent online almost immediately; full bootstrap (cold, no build cache) around 3 minutes; a warm re-run (cache hit) under a minute.

Self-modifying script gotcha: a code change to ec2-bootstrap.sh needs two triggers to actually take effect on an already-running box. The script's own first real action is git reset --hard origin/main, which rewrites the very file the running process is executing. The already-running process keeps reading its own stale in-memory/buffered copy to completion — so the first trigger after a push correctly updates the repo on disk, but still runs the old logic end to end (observed live during Stage 5: a first re-trigger after deleting plain.conf/tls.conf still tried to cp the now-deleted file, and separately, a first re-trigger after adding LLM_PROVIDER=google to the .env heredoc still rendered .env without it). A second systemctl reset-failed aitutor-bootstrap.service && systemctl start aitutor-bootstrap.service reads the file fresh and runs correctly. A full aws ec2 reboot-instances does not have this problem — systemd starts a genuinely new process reading the current file from the start. When in doubt after changing this script, trigger it twice, or reboot instead of using the SSM one-liner.

Watch it live:

# from a laptop with an active SSM session to the box
aws ssm start-session --target <instance-id> --region us-west-2
sudo journalctl -u aitutor-bootstrap.service -f

3. Health checks

HTTP 200 from curl is not evidence the site works. This is not a hypothetical - it happened. The deployed frontend once served a blank white page to every single visitor while every curl-based check in this document reported success. Cause: terraform/frontend.tf's CloudFront response-headers policy set script-src 'self' with no 'unsafe-inline'. Next.js's static export bootstraps through inline <script>self.__next_f.push(...)</script> tags carrying the RSC flight payload - CSP blocked all of them, React threw Error: Connection closed., and the server-rendered markup was wiped. curl -sI against the page still returned a clean 200 the entire time, because curl neither executes JavaScript nor enforces CSP - it only ever saw the initial HTML, not what the browser did with it after. Fixed to script-src 'self' 'unsafe-inline' (see the comment above aws_cloudfront_response_headers_policy.frontend in terraform/frontend.tf), applied, CloudFront invalidated. Every curl-based check below only verifies that a server responded - none of them can catch a client-side rendering failure like this one. Load the deployed page in a real browser and confirm visible text is present before trusting any curl result as "the site works."

One-command "is it up", no interactive session needed:

aws ssm send-command --region us-west-2 --instance-ids <id> \
  --document-name AWS-RunShellScript \
  --parameters commands='["cd /home/ec2-user/AITutorApp && docker compose ps"]'
# then: aws ssm get-command-invocation --command-id <id-from-above> --instance-id <id>

Or interactively: aws ssm start-session --target <id> --region us-west-2, then cd AITutorApp && docker compose ps. Healthy looks like all four containers Up, with api and db additionally showing (healthy) — nginx and streamlit have no healthcheck defined, so "running" is the only signal for them.

4. Promoting code from GitHub to prod

Suggestions only — nothing below is implemented.

The image is built on the box, not locally or in AWS CI. There is no ECR, no CodeBuild, no separate build step anywhere. docker compose up -d --build on the EC2 instance itself is the entire build pipeline.

Today's actual promotion path

  1. Merge to main, push.
  2. Trigger the box to pick it up — there is no automatic boot anymore (§2), so this step is never optional: 
    aws ssm send-command --region us-west-2 --instance-ids <id> \
  --document-name AWS-RunShellScript \
  --parameters commands='["sudo systemctl reset-failed aitutor-bootstrap.service", "sudo systemctl start aitutor-bootstrap.service"]'
# if this is the box's first pull of a change to ec2-bootstrap.sh
# itself, run the same command a second time - see the self-modifying-
# script callout in §2.

That's the whole thing. Observed cost this stage: roughly 1–3 minutes depending on build-cache warmth, with automatic rollback-free re-seeding folded in for free. This is genuinely simple, which is the strongest argument for leaving it alone.

5. Changing prod data

Safe mid-exam Adding or editing a participant. prod/seed_participants.py only ever touches token/name/identifier/group/intervention — it never writes status, active_session_id, started_at, or last_seen_at on a row that already exists, so a live student's session is untouched by a re-seed.
Not safe mid-exam Changing server_ready_questions.csv under a student who is mid-attempt. Questions load into memory once at api boot (app/main.py); nothing reloads them live, deliberately — silently swapping questions under an in-progress student would be worse than requiring an explicit restart.

Participants

# 1. edit prod/data/participants.csv locally
# 2. mint tokens + upsert manifest (.venv active, local DB running)
python prod/generate_tokens.py

# 3. push to S3 and re-seed the live box, no reboot — ~10 seconds
./scripts/update-prod-data.sh

update-prod-data.sh syncs prod/data/ to s3://aitutor-434195712367-ops/artifacts/prod-data/, then finds the running instance by the aitutor-app tag and runs prod/seed_participants.py on it over SSM. If the box is currently stopped (normal between exams), it just updates S3 and logs that the next boot will pick it up automatically — no error, no manual follow-up needed.

Questions

# 1. edit prod/data/new_evaluation_questions.csv locally
# 2. regenerate the server-ready CSV
python prod/prepare_data.py

# 3. push to S3 (update-prod-data.sh does not do this part today)
aws s3 sync prod/data/ s3://aitutor-434195712367-ops/artifacts/prod-data/ --region us-west-2

# 4. pick up the change — restart, not a full rebuild
aws ssm send-command --region us-west-2 --instance-ids <id> \
  --document-name AWS-RunShellScript \
  --parameters commands='["cd /home/ec2-user/AITutorApp && docker compose restart api"]'

Source PDF (RAG corpus)

Replacing prod/data/source.pdf and restarting api re-triggers ingestion automatically — ingest_pdf() checks whether it's needed on every boot. Measured cost for the current 7-page source: about 2 seconds. Follows the same S3-sync-then-restart path as questions above.

5b. Backups — what "nightly" actually means

The nightly cron is not the safety net. 0 2 * * * only runs while the instance is running, and this box is stopped between exams by design. Instance stopped: no backups fire at all. A single-day, 25-minute exam very likely never crosses 02:00 while the box happens to be up. Do not describe this cron as coverage in an incident.

The real protection is a dump taken immediately before stopping the box. While the box is stopped, data physically cannot change, so a pre-stop dump is current for the entire stopped period by definition. This is §10 step 8 — do it every time, not just after an exam.

Fixed during Stage 5 (previously a real gap, F2 in the migration plan): BACKUP_S3_URI now correctly points at aitutor-backups-<account-id> (a dedicated Terraform-managed bucket, terraform/backups.tf), not the ops bucket. The instance role previously had no PutObject permission on the ops bucket at all, so every nightly `aws s3 cp` silently failed with AccessDenied — backup.sh exited non-zero under set -e, and the failure landed only in backups/cron.log, which nothing monitors. Before this fix, the system would have looked like it had off-box backups and had none. The instance role's IAM policy also now grants GetObject/ListBucket on the backups bucket (previously write-only, so nothing on the box could even read a backup back — no restore path existed at all).

Verify a dump actually landed:

aws s3 ls s3://aitutor-backups-<account-id>/backups/ --region us-west-2
Verified live, 2026-08-04: the backups bucket is empty. No off-box copy of production data exists right now. s3://aitutor-backups-434195712367 contains zero objects. The nightly cron mechanism is correctly wired end to end (IAM fix above, correct bucket, correct permissions) - it has simply never had the chance to fire, because the box has not been left running across a 02:00 boundary since the fix landed. Separately, restore_drill.sh has only ever been exercised against the DEV database - it has never validated a restore of a real prod-sourced dump. Do not treat "the cron is fixed" as "a backup exists." Until a dump is actually visible in this bucket, the only real protection is the manual pre-stop step in §10: run scripts/backup.sh and take an EBS snapshot before every stop-instances, no exceptions, and confirm the object landed with the command above before walking away.

No alert fires when the cap is approached; it just starts rejecting hint/chat requests. Worth a manual glance mid-exam if usage looks unusually heavy.

9. Streamlit admin — what you can and cannot do

Reach it (never exposed publicly — 127.0.0.1:8501 on the host):

aws ssm start-session --target <id> \
  --document-name AWS-StartPortForwardingSession \
  --parameters portNumber=8501,localPortNumber=8501 \
  --region us-west-2
# then open http://localhost:8501
Two prerequisites that are easy to miss, and both fail confusingly

Every aws command in this runbook needs a region and valid credentials. Without a region the CLI fails with NoRegion before it does anything else, which is why --region us-west-2 is written out on every command here. If you authenticate through SSO rather than a default profile, add --profile <your-sso-profile> too, or export AWS_PROFILE once for the shell.

start-session additionally needs the Session Manager plugin, a separate binary the AWS CLI shells out to. It is not bundled with the CLI and not installed by anything in this repo. Without it you get SessionManagerPlugin is not found, which looks like a permissions or SSM problem but is purely a missing local binary. On macOS: brew install --cask session-manager-plugin. No shell restart is needed, the CLI resolves it on PATH at call time.

Both of these were hit live on 2026-08-04 while opening Streamlit, in that order. Anything in this runbook that depends on start-session, including the exam-day Streamlit tunnel, is blocked until the plugin is installed, so install it well before exam day rather than discovering it under time pressure.

It bypasses the API entirely Streamlit talks straight to Postgres (streamlit_app/app.py), not through FastAPI — none of the API's row-level authorization applies here. That's by design (it's the trusted admin path), but it means every action below is unguarded: no confirmation dialogs on destructive buttons beyond Streamlit's own click-to-submit.

Can

  • View system-wide analytics: A/B distribution, hint-style preferences, per-user summary, correctness %
  • Exam Control: bulk-extend (or reduce) every unsubmitted session's timer at once, with an affected-count preview
  • View LLM usage (24h rolling, global + top consumers)
  • Export any of Interaction/Chat/Intervention/Action logs as CSV, filtered by user/date/type
  • Per student: view full profile, skill-mastery trajectory, interaction history, hints & interventions, chat log, action log
  • Per student: edit A/B group, hint-style preference, intervention preference
  • Per student: Reset Timer to NOW, Adjust Timer (± minutes), Clear Session Lock
  • Per student: Reset Progress (wipes interaction history + mastery, resets to unused) — irreversible
  • Per student: Delete User — permanently, irreversible

Cannot — use instead

  • Add/edit participants → update-prod-data.sh (§5)
  • Change questions → S3 sync + docker compose restart api (§5)
  • Restart/stop/start any service → SSM + docker compose (§2, §8)
  • Read container/boot logs → docker compose logs / journalctl (§6)
  • Change env config (API keys, LLM caps, CORS origin) → edit .env on the box over SSM, then restart
  • Take or restore a backup → scripts/backup.sh / restore.sh (§8)
Research data export gap: there is no one-command way to get all research data off the box. Two partial paths only, verified against streamlit_app/app.py:
  • A full pg_dump via scripts/backup.sh - complete, but the output is a Postgres dump; you need a Postgres to restore it into before you can query anything out of it.
  • Streamlit's Export Data view - CSV export, filtered by user/date, but only for Interaction Logs, Chat Logs, Intervention Logs, and Action Logs (the exact four options in its log_type selectbox), one type at a time, and it needs an SSM port-forward to a currently-running box.

SkillMastery has no bulk export at all - confirmed by reading the export view's code: it is not one of the four log_type options. It is only viewable per student, in that student's Skill Mastery tab, as an on-screen line chart plus a raw-data table inside an expander - and that per-student view has no st.download_button either, unlike the Interaction History and Chat Log tabs next to it. The only way to get skill_mastery rows out today is a direct Postgres query - either docker compose exec db psql -U aitutor -d aitutor_db -c "SELECT * FROM skill_mastery;" over an SSM session, or restoring a pg_dump and querying the table there.

10. Exam day runbook

Sequenced from PRELAUNCH_CHECKLIST.md §K, folded into one list:

  1. Snapshot before starting. Take an EBS snapshot of the current (stopped) volume before aws ec2 start-instances, so there's a clean pre-exam restore point.
  2. Start the instance, watch aitutor-bootstrap.service complete over SSM (§2, §3).
  3. Confirm EXAM_DURATION_MS on the box reads 1500000 (25 minutes), not a leftover 20-minute default, and LLM_PROVIDER reads google (see §8's incident row — the code default is the wrong provider): docker compose exec api env | grep -E "EXAM_DURATION_MS|LLM_PROVIDER".
  4. Smoke test one real token end to end — login, answer, hint, chat, submit, results — before handing tokens to students. Check the actual hint/chat content, not just the HTTP status: a 200 with hint_style: "error" means the LLM call silently failed.
  5. Expect a slow first hint. RAG cold start is ~2s measured, but the first real request after boot still pays container warm-up cost on top. Not a bug if the very first hint feels sluggish.
  6. Keep an SSM session open to the box and a port-forward tunnel to Streamlit (§9) for the full exam window, so timer/lock issues can be handled in real time.
  7. Immediately before stopping the instance: take an EBS snapshot and run ./scripts/backup.sh (with DOCKER_DB_SERVICE=db). This is the real backup, not the nightly cron (§5b) — while the box is stopped the data cannot change, so a dump taken right before stopping stays current for the entire stopped period.
  8. Stop the instance once data is safely off-box. It should not sit running between exams.

A process note worth keeping, not just a code recommendation Two real incidents this stage were the same bug class: a shell pipeline under set -o pipefail where one stage (grep -m1, or grep -v on empty input) exits non-zero for a benign reason and silently kills the whole script. Worth a quick pipefail-audit pass — grep -n '|.*|' scripts/*.sh terraform/templates/*.tftpl as a starting point — any time these bootstrap scripts are next touched.
AWS catalog drift is real, not hypothetical The Stage 4 plan sized the root EBS volume at 20GB; by Stage 5's apply, AWS's current AL2023 AMI (fetched via most_recent = true) needed 30GB just for its own snapshot. Nothing in the repo changed — Amazon's base image did. Worth a terraform plan drift check before any future apply that's been sitting for a while, even with no local changes.
Config-default traps are a real bug class here, not a one-off LLM_PROVIDER (§8) is the same failure shape as three items already fixed earlier in this project (LOG_LEVEL, EXAM_DURATION_MS, GOOGLE_MODEL_NAME — see PRELAUNCH_CHECKLIST.md §H): .env.docker.example documents the required value, but scripts/ec2-bootstrap.sh's .env heredoc never actually wrote it, so the code-level fallback silently took over in production. The other three were caught because their fallbacks happened to be safe ones close enough to correct not to break anything visibly; LLM_PROVIDER's fallback (ollama) was actively wrong and broke the entire tutoring feature, just quietly enough (hints has a fallback path, chat doesn't) that nothing caught it until this stage tested chat against a real deployed box for the first time. Recommended: a one-time diff between every key in .env.docker.example and every key ec2-bootstrap.sh actually writes, and a boot-time assertion (matching the existing APP_ENV=production pattern in app/main.py's lifespan) that fails loudly rather than silently degrading whenever LLM_PROVIDER != "google" in production.
